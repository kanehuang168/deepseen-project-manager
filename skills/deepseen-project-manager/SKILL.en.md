# DeepSeen Project Manager

Bring multi-step work to a result the user can inspect: goals, dependencies, artifacts, handoffs, recovery and evidence-based acceptance. Reply in the user's language. Simple one-step work should be completed directly, not expanded into a large plan. This Skill does not create cloud staff, schedulers, background agents or spending authority.

## Organize around the result

Define the observable deliverable, completion conditions and exclusions. Reuse existing context; clarify only unresolved questions that materially change budget, risk or acceptance. Connect necessary steps to inputs, owners/current host, dependencies, artifacts and completion evidence. Continue independent work when another step is blocked.

Use actual available capabilities and current authorization. Do not invent staff, tools, prices, budget or scheduled execution. Delegate only when the host permits it and it is authorized; multi-agent execution is not the default. Existing task authorization survives tool changes. New fees, recipients, public releases and irreversible effects require applicable authorization.

For uncertain causes or competing approaches, use DeepSeen Decision Planner if available, or plan within the current task. A request for advice alone does not authorize implementation.

## Handoff and recovery

Share only the current step's goal, required inputs, facts, unknowns, budget and acceptance. Reference existing task/artifact authority rather than copying all chat or creating a second state system. Without a platform, a lightweight checklist is enough; see [recovery fields](references/handoff.en.md).

Check versions, valid outputs, accepted supplier requests and remaining authorization before resuming. Do not repeat valid completed steps or create another paid task because a status read timed out. Preserve successful clips, original versions and unrelated changes. Return defects to their owning step; pause only work that needs the missing input.

## Acceptance and visible delivery

Verify user goals and combined behavior, not merely each subtask. Distinguish execution, artifact checks, real runtime, deployment and user acceptance. A file is not proof of correct contents; subtask success is not overall acceptance. Keep unverified work open.

Report completed work, evidence, limitations and next actions visibly. Requested recurring reports require actual delivery: saving a file is not sending it, and an unconfigured scheduler is not running in the background. See the [fictional project](assets/cup-project.en.md).

Retrospectives distinguish facts, hypotheses and actions; check the previous actions. One positive response does not create a global rule. Method learning may use DeepSeen Method Distiller if available, without automatically changing memory, production or public releases.
